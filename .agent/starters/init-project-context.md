# 自动初始化项目上下文

## 当前模式

你现在处于“项目上下文审计与初始化模式”。

你的目标是根据当前仓库中已经存在的代码、配置、依赖、测试和部署文件，初始化或完善：

`.agent/project-context.md`

这份文件描述的是项目当前已经成立的事实，不是未来技术选型、理想架构或重构方案。

## 授权范围

本次明确授权你修改：

`.agent/project-context.md`

如果该文件不存在，可以读取 `.agent/templates/project-context.md` 并据此创建。

除此之外：

* 不修改任何应用源码、测试、依赖、配置、数据库、部署文件或公共文档；
* 不修改 `AGENTS.md`；
* 不修改 `.agent/` 下的其他文件；
* 不创建重构代码或迁移；
* 不安装依赖；
* 不启动服务、部署、提交或推送 Git；
* 不把本次审计自动扩展为修复任务。

允许执行只读仓库检查，例如文件搜索、依赖检查、Git 状态检查和配置读取。

## 开始前读取

请先完整读取：

1. 根目录 `AGENTS.md`；
2. `.agent/prompts/shared-engineering-rules.md`；
3. 当前 `.agent/project-context.md`；
4. 与技术栈、运行方式和架构有关的仓库文件。

当前由开发者明确提供并应默认保留的项目事实是：

* 项目名称：`XingryBot`
* 项目目标：可以完成各项功能的 Telegram 机器人，对最终用户呈现猫娘形态
* 最终用户：Telegram 中文用户
* 当前阶段：`development`
* 部署形态：`cloud`
* 部署环境：云服务器

除非仓库证据与这些内容存在明显冲突，否则不要覆盖这些人工填写的事实。发现冲突时，在最终报告中列出，由开发者裁决。

## 审计范围

根据仓库实际存在的文件选择性检查，不要机械读取所有文件。

重点检查：

* `pyproject.toml`
* `requirements*.txt`
* `poetry.lock`
* `uv.lock`
* `Pipfile*`
* `.python-version`
* `package.json` 及锁文件
* `Dockerfile*`
* `compose*.yml` 或 `docker-compose*.yml`
* CI 配置
* 服务启动脚本
* systemd 或其他部署配置
* 程序入口
* 主要源码目录
* 数据库初始化和模型
* 配置加载方式
* 测试目录
* Lint、格式化和类型检查配置
* 日志初始化
* 时间与时区处理
* 用户文案、模板和产品 Prompt
* `.env.example`

可以读取 `README*` 和现有文档作为辅助信息，但代码、依赖文件、锁文件、构建配置和真实入口优先于可能过期的文档。

禁止读取或输出：

* `.env` 中的值；
* 密钥、Token、Cookie、私钥和凭据；
* 数据库中的个人数据；
* `.git/` 内部对象；
* `node_modules/`；
* 虚拟环境；
* 构建产物；
* 缓存目录；
* `.agent-work/` 中与本次初始化无关的历史调试内容；
* 大型生成文件和二进制文件。

可以根据 `.env.example` 记录配置项名称，但不得记录真实秘密值。

## 证据与填写规则

对每个字段，必须选择以下状态之一：

### 1. 已验证

仓库中存在直接证据。

例如：

`Python 3.11（由 pyproject.toml 的 requires-python 确认）`

### 2. 基于证据推断

没有直接声明，但可以从入口、导入关系或配置可靠推断。

例如：

`推断为 pip 管理依赖（存在 requirements.txt，未发现 Poetry 或 uv 配置）`

不要把推断写成确定事实。

### 3. 未配置

项目当前没有对应工具或能力。

例如：

`未配置独立的类型检查`

### 4. 尚未决定

这属于未来产品或架构决策，当前仓库没有答案。

例如：

`尚未决定生产环境的容器编排方式`

### 5. 不适用

该字段不适用于当前项目。

例如：

`不适用：当前为 Telegram Bot，没有独立 Web 前端`

不得保留 `<framework-and-version>`、`<command>` 等占位符。无法确定时必须使用上述明确状态，而不是猜测。

## 各章节的具体要求

### 1. 项目基本信息

保留开发者已经填写的内容。可以根据仓库补充更准确但不扩大范围的描述。

猫娘属于最终用户交互形态，不代表后台日志、API、错误信息和代码注释也应使用猫娘语气。

### 2. 技术栈

根据实际依赖和入口填写：

* 是否存在独立前端；
* 后端或 Bot 服务使用的语言、框架和主要库；
* 数据库及访问方式；
* 当前实际使用的包管理方式；
* 运行时版本及其证据；
* 当前已经存在的部署方式。

依赖没有固定版本时，写明“版本未锁定”，不要查询互联网后填入最新版。

### 3. 主要目录与职责

只列出对理解项目有实际价值的主要目录和入口文件，不要把整个文件树复制进表格。

每条职责必须通过代码或配置确认。

### 4. 常用命令

只填写可以从以下位置确认的命令：

* 包管理器脚本；
* Makefile；
* Dockerfile 或 Compose；
* CI；
* 测试、Lint、格式化配置；
* 明确的程序入口；
* 当前可信的开发文档。

如果命令只是根据入口推断，标注“推断，尚未执行验证”。

没有相应能力时写：

* `未配置单元测试`
* `未配置集成测试`
* `未配置 Lint`
* `未配置类型检查`
* `不需要独立构建步骤`

不得为了填满表格而发明命令。

### 5. 架构与约定

描述当前代码实际呈现出的架构，包括：

* 入口和启动流程；
* 命令处理、服务、数据访问、配置等模块之间的关系；
* 当前依赖方向；
* Telegram Bot API 或其他外部 API 的调用方式；
* 错误如何处理；
* 日志如何配置；
* 测试当前如何组织；
* 代码中占主导地位的命名与格式。

如果项目尚未形成统一约定，应如实写：

`当前尚未形成统一错误协议，各模块分别处理异常`

不要把建议中的理想架构写成当前架构。

### 6. 用户上下文与本地化

检查：

* 用户语言是否存储；
* Telegram 用户的语言信息是否被读取；
* 用户时区是否存储；
* 当前是否写死中文；
* 当前时间使用 UTC、固定 UTC+8、系统时区还是 IANA 时区；
* 数据库存储和用户展示分别采用什么策略。

如果代码使用固定 `timezone(timedelta(hours=8))`，应记录为：

`当前使用固定 UTC+08:00 偏移，尚未采用 IANA 时区`

不要擅自把它改写成“Asia/Shanghai 已实现”。

### 7. 内容与 Prompt 管理

检查用户文案、猫娘角色文本、回复模板和模型 Prompt 当前存放在哪里。

如实记录：

* 集中式资源文件；
* 分散在处理函数中的硬编码字符串；
* 数据库存储；
* 配置文件；
* 当前没有模型 Prompt；
* 当前不支持运行时编辑。

这里只记录现状。需要外置、国际化或重构的内容放入“已知问题与风险”，不要在本次任务中实施。

### 8. 保护范围

保留已有保护规则，并根据项目事实补充：

* 凭据文件；
* 数据库文件；
* 生产配置；
* 用户数据；
* 部署文件；
* 不能破坏的 Telegram 命令和数据兼容性。

不要自行宣布禁止某项技术，除非开发者、现有配置或仓库规范已经明确禁止。

### 9. 已知问题与风险

只记录当前仓库证据能够支持的问题，例如：

* 依赖版本未锁定；
* 没有测试；
* Token 可能从错误位置加载；
* 用户文案分散在代码中；
* 固定 UTC+8 不支持其他时区；
* 数据库路径依赖当前工作目录；
* 异常处理不一致；
* 日志可能输出不必要的用户信息；
* 猫娘角色文案与后台错误信息混合。

不要添加与当前仓库无关的通用风险清单。

按实际影响排序，优先保留 3 至 8 项最有价值的风险。

## 写入前检查

完成仓库审计后：

1. 先在回复中简要说明发现了哪些技术事实；
2. 如果人工填写内容与仓库存在重大冲突，先报告冲突，不静默覆盖；
3. 对其余字段直接完成初始化，不因次要未知项阻塞；
4. 只修改 `.agent/project-context.md`。

## 写入后验证

写入后必须检查：

1. 文件中不再存在 `<...>` 占位符；
2. 没有写入秘密值、Token、私人数据或 `.env` 内容；
3. 填写的路径真实存在，或者已经明确标注为“未配置”；
4. 命令有仓库依据，推断命令已标注“尚未执行验证”；
5. 当前事实与未来建议没有混写；
6. 人工填写的项目目标和用户信息没有被无理由覆盖；
7. Git Diff 中只有 `.agent/project-context.md` 被修改。
