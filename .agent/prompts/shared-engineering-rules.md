# 共享工程准则

## 1. 适用范围与术语

这些规则适用于规划、实现和复核 Agent。

- “开发者”：当前项目的维护者或提出工程任务的人。
- “最终用户”：部署后实际使用产品的人。
- “用户可见内容”：UI 文案、聊天回复、通知、邮件、导出内容等。
- “机器接口”：API、事件、日志、错误码、队列消息和内部协议。
- “Agent 产物”：规划、调试、交付和验收过程中产生、但不属于产品运行时的文件。

平台的更高优先级规则、安全边界和当前开发者明确指令始终优先。若当前任务与这些准则冲突，指出具体冲突并请求开发者裁决，不要静默选择。

## 2. 先理解项目，再选择实现

先读取任务相关的现有代码、配置、测试和项目约定。优先延续现有架构、设计系统、依赖策略、错误协议和命名规则。

只修改完成当前任务所必需的范围。不要顺手重构无关模块、添加未要求功能、替换技术栈或制造新的抽象层。需要扩展性时，围绕已经明确存在的变化轴设计，而不是为假设中的未来需求过度工程化。

## 3. 语言、地区与时间

凡是与最终用户相关并可能因用户、租户、地区或部署环境变化的语言、地区、日期和时间行为，不得在业务逻辑中写死。

默认解析优先级为：

1. 已认证最终用户的显式设置；
2. 租户或应用级设置；
3. 当前请求、浏览器或设备提供的可靠上下文；
4. 部署配置；
5. 项目声明的明确默认值。

服务端内部存储、比较、排序和跨系统传输优先使用 UTC 或携带明确时区偏移的标准格式。面向最终用户展示时，转换为用户时区并使用用户地区格式。优先使用 IANA 时区标识，不依赖含义不稳定的缩写。

云端运行环境只是在缺少更具体上下文时的系统级回退，不能覆盖已知的最终用户设置。定时任务必须明确属于系统、租户还是用户作用域，并据此选择时区。

新增语言或地区支持应主要通过语言包、消息目录、格式化器、Locale 注册表和回退链完成，不应要求修改核心业务流程。避免拼接难以翻译的用户句子。

## 4. 文件修改边界

除非开发者或任务契约明确要求，不得创建或修改面向使用者和维护者的公开文档，包括但不限于：

- `README*`；
- `CHANGELOG*`；
- `LICENSE*`；
- 公共 `docs/`；
- 发布说明、贡献指南和项目规划文档。

完成工程任务所必需的源码、测试、Schema、数据库迁移、配置、依赖清单、锁文件、构建脚本和部署文件可以在任务范围内修改。

不得把产品源码、运行时资源或必要测试放入 Agent 工作目录。任务级计划、临时脚本、调试输出和报告统一放在 `.agent-work/tasks/<task-id>/`。不得在项目其他位置散落临时文件。

`AGENTS.md` 和 `.agent/` 是开发者拥有的 Agent 配置。除非任务明确要求维护 Agent 工作流，否则不得修改。

## 5. 人格与运行时输出分离

开发者要求 Agent 使用的语气、角色或人格，只影响 Agent 与开发者交流的方式，不得自动进入产品源码、注释、数据库内容、API 封装、日志、错误信息或运维输出。

如果产品需求明确要求部署后的用户界面或聊天内容具有特定人格，只允许用户可见的内容层体现该人格。后端协议封装、状态字段、错误码、日志和内部事件仍应保持中性、稳定、简洁、结构化。

当后端承载角色化用户文本时，把它放入语义明确的内容字段；不要让传输协议本身角色化。

## 6. 可变内容与代码分离

不要机械地把所有字符串移出代码。按照内容性质选择位置：

- 稳定的协议常量、错误码、枚举和技术标识保留在代码中；
- 用户可见、需要翻译、经常调整的纯文本放入版本化资源或模板；
- 产品模型 Prompt 集中放入专用 Prompt 模块或资源层，并对动态变量进行类型或 Schema 校验；
- 需要不重新部署即可修改的内容使用数据库、CMS 或受控配置服务；
- 密钥、令牌和敏感配置使用环境变量或密钥管理系统，绝不写入文案和 Prompt 文件。

外部内容应具有缺失回退、加载失败处理、版本管理和必要测试。不要通过外置文件把类型错误从编译期推迟到生产环境。

## 7. 后端与机器输出

机器输出应遵循现有协议并保持：

- 字段含义明确；
- 错误码稳定；
- 必要上下文充分但不过度泄漏内部信息；
- 适合程序解析；
- 日志级别、请求标识和关联信息合理；
- 不包含无意义寒暄、角色口癖或重复自然语言。

最终用户文案尽量在表现层或内容层完成本地化。核心业务层优先返回稳定状态、代码和结构化数据。

## 8. 验证要求

验证必须与实际改动匹配，至少考虑：

- 改动行为的针对性测试；
- 相关回归测试；
- 类型检查、Lint 和构建；
- 缺失用户设置时的回退；
- 时区边界和夏令时；
- 翻译键缺失与语言回退；
- API 或事件 Schema 稳定性；
- 角色化文本是否泄漏到日志和机器接口；
- Agent 临时产物是否被 Git 跟踪；
- UI 改动的实际渲染、响应式状态、加载态、空态和错误态。

不能运行的验证必须明确说明原因和下一种最可信的检查方式。没有真实执行证据时，不得声称测试已经通过。
